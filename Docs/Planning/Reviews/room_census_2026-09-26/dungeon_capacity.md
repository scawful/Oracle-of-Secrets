# Oracle of Secrets — Dungeon Capacity Analysis (non-room-count limits)

Scope: every engine/SRAM/table limit that caps "how many dungeons" Oracle of Secrets
can hold, EXCLUDING free-room-count (covered by a separate agent). Read-only analysis;
no ROM/asm edits made. ROM used for `z3ed` probes: `Roms/oos168x.sfc` (Asar-patched
build, read-only queries only). Base ROM: `Roms/oos168.sfc`.

## Bugs / data-quality issues found along the way (not asked for, but load-bearing for #7 and dungeon-ID bookkeeping)

1. **`Docs/Technical/Room_Tag_Slots.md` has the wrong tag IDs for 4 of its 6 listed addresses.** It assumed a naive sequential numbering (`0x33,0x34,0x35...`) starting at `$01CC00`. The real vanilla jump table (`usdasm/bank_01.asm:12241-12305`) gives non-sequential IDs: `$01CC00=0x21`, `$01CC04=0x23`, `$01CC08=0x34`, `$01CC0C=0x35`, `$01CC10=0x36`, `$01CC14=0x37`. Only the last two entries in the doc (`$01CC18=0x39`, `$01CC1C=0x3A`) happen to be correct.
2. **`Sprites/Objects/minecart.asm:1488-1500` documents its own hook as "Tag 0x38 at $01CC14"**, but `$01CC14` is actually vanilla tag ID `0x37` (`RoomTag_Holes6`); tag ID `0x38` is `RoomTag_Agahnim`, a different address entirely. Any dungeon room whose header tag byte is set to `0x38` expecting "cart-required shutter" behavior will **not** get it (it hits the real Agahnim-door routine instead); the working tag ID for that feature is actually `0x37`. This should be fixed in the source comment and re-checked against whatever room headers currently carry tag `0x38` in yaze.
3. **Entrance `0x0C` reports `dungeon_id: 0x09`** (room `0x0053`) — an odd value, inconsistent with the even-ID convention documented everywhere else (`Core/ram.asm:1972`, "Dungeon IDs, multiples of 2"). `Docs/World/Shrines/ShrineofCourage.md` says entrance `0x0C` is "shared with Fortress of Secrets," but FOS's real ID is `0x1A` (verified), not `0x09`/anything reachable from `0x0C`. This room likely still carries stale/unconverted vanilla Skull Woods data. Not chased further; flagged for whoever next touches Shrine of Courage.
4. `Docs/Dev/Planning/dungeons.json`'s `vanilla_name` field is stale for several dungeons (e.g. claims D2 Tail Palace = "Ice Palace" and gives its entrance as `0x0E`, which is actually a cave (`dungeon_id 0xFF`) at room `0x00F3`). The `sram.asm` comment block (dated 2026-09-26) and the `z3ed`-verified IDs in this report are more current/authoritative; the JSON should be regenerated, not trusted for dungeon-ID mapping.

## The binding constraint(s)

**Primary binding constraint: the vanilla small-key SRAM array (`$7EF37C-$7EF389`, 14 bytes, one per dungeon ID) is read/written with zero bounds checking by the death-respawn and room-entry routines.** This — not room count, not ROM space, not entrance IDs — is what actually caps how many *keyed* dungeons Oracle can add before something breaks:

- Oracle has used 10 of the 14 vanilla dungeon-ID slots.
- **3 more full dungeons** (with working small keys AND compass/map/big-key tracking) fit for free using IDs `0x00` (Sewers), `0x04` (Eastern Palace), `0x08` (Agahnim's Tower) — zero SRAM/table changes required.
- A 4th slot, `0x02` (Hyrule Castle), is usable but its key counter is hard-aliased to `0x00`'s by vanilla code — fine only if that 4th dungeon is happy sharing a key pool with whichever of the first 3 uses `0x00` (or is itself keyless).
- Beyond that, `0x1C`/`0x1E` give **compass/map/big-key tracking for free** (the vanilla `DungeonMask` table already reserves them) but **not** working small keys — using them for a keyed dungeon without a hook will silently corrupt `FishingRod` (`$7EF38A`) or `Bananas` (`$7EF38B`) SRAM the first time a player dies and respawns inside that dungeon, and will also corrupt `GamesCurrentSegment` (`$7EF3FF`) via the parallel 14-slot "games played per dungeon" array (`$7EF3E3-$7EF3FD`) if that ever gets exercised.
- The crystal-award table (`RoomTagPrizeChecks`) is separately capped at 13 dungeon-eligible entries with no free tail bytes — relevant only if a new dungeon wants a *crystal* (vs. pendant or a bespoke SRAM flag) reward.

Everything else checked (entrance table, room tags, room object/sprite/collision banks, palace-map bank, room flags) has generous headroom and is not what will run out first.

## Cheap ways around the binding constraint

1. **Use the 3 free "clean" dungeon IDs first** (`0x00`, `0x04`, `0x08`) for the highest-priority new full dungeons (e.g. the tall Sky Islands tower) — this needs zero SRAM restructuring, just point the new rooms' headers at one of these IDs and update `Core/sram.asm` aliases (`KeysSewer`/`KeysDesert`(wait: `0x04`=`KeysEastern`)/`KeysAgahnim`) to the new dungeon's real name.
2. **Make additional dungeons keyless** (no small-key doors — only a big key/compass/map or nothing at all). A keyless dungeon can safely use `0x1C` or `0x1E` today with **zero code changes** (compass/map/big-key already work; the never-executed key-array write for those IDs simply never fires because there's no key to give).
3. **Reuse an existing dungeon ID for a mini-dungeon/shrine**, exactly as Oracle already does (Shrine of Wisdom reuses the Tower-of-Hera slot `0x14`; Shrine of Power reuses the Desert Palace slot `0x06`). A new underwater shrine or extra pendant shrine can share any of the 10 in-use IDs as long as it doesn't need its own independent key/compass/map state — award a **pendant bit** (5 free) or a **plain SRAM flag** (327 documented free bytes in `Core/sram.asm` §10) instead of a crystal/compass/map bit.
4. **If a keyed dungeon beyond the 3-4 free slots is required**, hook the two raw indexing sites (`usdasm/bank_09.asm:21405-21415` and `usdasm/bank_02.asm:390-403`) to redirect any dungeon ID ≥ `0x1C` to a small relocated key-count table elsewhere in SRAM (e.g. carved out of `FreeBlock_Large`/`FreeBlock_Dreams`, both already documented as free in `Core/sram.asm`). This is a well-scoped, one-time ASM patch — not free, but cheap, and exactly the kind of hook Oracle's codebase already does dozens of times over.
5. **Skip the crystal table entirely for new dungeons.** Only the original 7 crystal dungeons need `RoomTagPrizeChecks`; give new dungeons a pendant, a mask, or a bespoke SRAM flag instead, sidestepping the 13-entry table's lack of free tail space.
