## 1. CPU state at hook entries/exits

All VERIFIED by reading the exact vanilla bytes being replaced and comparing
byte counts.

**`$068365` (`Sprite_Main`, after `OAM_ResetRegionBases`/`Garnish_ExecuteUpperSlots_long`).**
Vanilla: `JSL Follower_Main` (usdasm `bank_06.asm:777`, 4 bytes). Replacement
`JSL P2_Tick` (`player2_hooks.asm:12`, 4 bytes) — same size. `P2_Tick`
(`player2.asm:151-168`) does `PHP : REP #$30 : PHA:PHX:PHY : PHB:PHK:PLB :
SEP #$30` on entry and the exact mirror `PLB : REP #$30 : PLY:PLX:PLA : PLP`
on exit, then `JML !P2_FollowerMain`. This is width-safe regardless of the
caller's actual M/X state — `PHP`/`PLP` round-trips the real flags — so no
entry-width assumption is even needed here. Stack balance: 3 pushes before
the two `JSR`s, 3 pulls after, `PLP` last — correct, and every internal
`JSR`/`RTS` pair inside (`P2_ReadPad`, `P2_Update`, `P2_Draw` and their
sub-calls) was spot-checked and balances (`RTS`/`RTL` pairing matches
`JSR`/`JSL`). DBR: `PHB:PHK:PLB` sets DBR = PBR = `$3A` for the duration,
restored via `PLB` before `JML`ing back into bank `$06`/`$09` code — correct
(vanilla `Follower_Main` expects its own DBR, not `$3A`'s).

**`$008B50` (`NMI_DoUpdates.no_update_swagduck`).** Vanilla: `LDX.w $0ADC :
STX.w DMA0ADDRL` (usdasm `bank_00.asm:1962-1964`, 3+3 = 6 bytes). Replacement
`JSL P2_NmiUpload : NOP #2` (`player2_hooks.asm:17`, 4+2 = 6 bytes) — exact
match. Entry width: `SEP #$30` is set at `bank_00.asm:1961` (labeled line
`.dont_toggle_oob`... actually the nearest one is `#_0089BE: SEP #$30`) and
`REP #$10` widens X/Y only at `#_0089E0`, giving **A 8-bit, X/Y 16-bit** at
`$008B50` — matches `player2.asm:1283`'s own entry comment exactly.
`P2_NmiUpload` (`player2.asm:1285-1330`) only ever does `REP #$20`/`SEP #$20`
(M-only) internally, never touching X/Y width, consistent with that
contract. DBR: NMI code runs with DBR = `$00` (SNES hardware invariant for
the native NMI vector in this engine, unaffected by the `JSL`), and
`P2_NmiUpload` uses `.l`/`.w` addressing correctly for that (`$2116`/`$4302`
etc. as `.w` because DBR=$00 covers the PPU/DMA register page; `P2_Magic`
etc. as `.l` since it's WRAM in bank `$7F`). Source bank restore: the routine
explicitly does `LDA.b #$7E : STA.w $4304` (`player2.asm:1307`) before
falling into the replayed `LDX $0ADC : STX $4302`, matching the "restores
DMA0 bank $7E" hook comment — VERIFIED, all paths through the routine (early
`BNE .done`, no-upload path, and the full-upload + optional blade-DMA path)
reach the replayed vanilla code with `$4304` correctly `$7E`.

**`$06F2C2` (`Sprite_CheckDamageFromLink`, after the layer check).** Vanilla:
`LDA.b $44 : CMP.b #$80` (usdasm `bank_06.asm:22483-22484`, 2+2 = 4 bytes),
with `BEQ .no_collision` at `$06F2C6` untouched. Replacement `JSL
P2_ActionGate` (4 bytes) — exact match, and the following `BEQ` in vanilla
ROM is left alone (only the `LDA`/`CMP` are overwritten). `P2_ActionGate`
(`player2.asm:674-696`) does `PHB:PHK:PLB` (DBR = `$06`, matching the routine
it's inlined into) then either falls through to the replayed `LDA.b $44 :
CMP.b #$80 : RTL` (miss path) or, on a hit, drops the JSL's 3-byte return
address (`PLA:PLA:PLA`) and `JML`s to `!P2_DamageExitHit` ($06F3C6, vanilla's
own "SEC, exit hit" tail) — correct idiom for "hook replaces a call and never
returns to it." Entry width A/X/Y 8-bit (comment at `player2.asm:672`):
consistent with the immediate byte compare `CMP.b #$80` in the replayed code
and with `bank_06.asm`'s per-sprite dispatch loop using 8-bit `X` throughout
(same DBR=`$06`/PHB:PHK:PLB block established earlier in `Sprite_Main`,
`bank_06.asm:068339-068341`, persists through the whole per-sprite loop —
not independently re-verified with a REP/SEP right at `$06F2C2` because none
exists there; the mode is inherited from the loop and never changed in
between).

**`$06F16F` (`Sprite_CheckDamageToLink.collision_checked`).** Vanilla: `LDA.w
$0E40,X` (3 bytes) : `BMI .exit_preserve_check` (2 bytes) : `BCC
.no_damage2` (2 bytes) = 7 bytes (usdasm `bank_06.asm:22197,22198... ` /
exact addresses `$06F16F-$06F175`, next instruction at `$06F176`).
Replacement `JSL P2_ContactGate : BCC P2_ContactNoDamage : NOP` = 4+2+1 = 7
bytes — exact match, `P2_ContactNoDamage = $06F1D7` (`player2_hooks.asm:28`)
is asar's own `.no_damage2` address (usdasm `bank_06.asm:22271`, `CLC:RTS`),
using a named label rather than a raw branch target (the project's own
documented asar gotcha about `BCC` + raw numeric targets, noted in the
memory file, correctly avoided here). Semantics VERIFIED bit-for-bit: `LDA
$0E40,X` sets N/Z only (not C), so carry entering `.collision_checked` is
whatever the earlier overlap-with-Link check left it at; `P2_ContactGate`
(`player2.asm:815-828`) replays that same `LDA`, branches on N exactly as
`BMI .exit_preserve_check` did (inverted to `BPL .damage_check`, logically
identical), and for the `BCS .link_hit` / no-damage-to-P2 paths ends with the
same carry semantics the vanilla `BCC .no_damage2` / fallthrough expected. A
1-byte `NOP` pads the branch to keep the total at 7 bytes, landing exactly at
`$06F176` either way. DB `$06`, A/X/Y 8-bit: same reasoning as the sibling
hook above (inherited from `Sprite_Main`'s loop-wide `PHB:PHK:PLB` /
`SEP #$30`, not independently re-set at this address in vanilla).

**SRAM.** `grep -n '7EF' Sprites/Players/player2.asm` (`player2.asm:850,965,
972,1346,1348,1349,1743`) shows only `LDA`/`CMP`/`SEC:SBC` reads of

`$7EF3CC` (follower active). A separate grep for any `STA`/`TSB` to a `$7EF`
address in the file returned nothing. VERIFIED: P2 never writes SRAM.

**Vanilla sprite table writes.** All indexed writes to `$0DD0,X` / `$0E20,X`
/ `$0D00-$0F80,X` etc. use an `X` that is either (a) the enemy slot passed in
by the vanilla routine that JSL'd into the hook (`P2_ActionGate`,
`P2_ContactGate`, `P2_PunchHitsSprite`, `P2_TryHurt`), never P2's own state,
or (b) P2's own held-object slot, obtained either directly from a vanilla
spawn call's return `X` (`P2_SpawnHeld`, `player2.asm:1656-1682`, `X` from
`JSL !P2_SpawnTerrain`) or re-derived through `P2_HeldSlot`
(`player2.asm:1840-1852`), which re-validates `$0E20,X == $EC` (kind) *and*
`$0DD0,X == $09` (P2's own "actively held" state) before trusting that slot —
so a slot P1 has since taken over (state becomes `$0A`) or that got reused by
something else is correctly rejected rather than corrupted. VERIFIED: no
cross-sprite corruption path found.

## 3. Lift / carry / throw

- **Duplication:** none found. `P2_Unstash` (`player2.asm:1697-1714`) always
  checks `P2_HeldSlot` first and skips re-spawning if the object is still
  alive (regroup / off-screen warp case), and forces `$0B9C = $FF` ("no
  secret") on the respawn-after-door copy specifically to avoid re-rolling
  the same secret twice.
- **Loss when the sprite table is full:** see Summary #2. `P2_TryLift`
  (`player2.asm:1596-1651`) pre-checks for a free slot (`.find_slot`,
  `1598-1601`) before calling the vanilla lift routines, but those routines
  (`Underworld_LiftAndReplaceLiftable` / `Overworld_HandleLiftableTiles`) can
  themselves spawn a secret into that same free slot before `P2_SpawnHeld`'s
  own internal search (inside `Sprite_SpawnThrowableTerrain_silently`) runs.
  If that happens, the tile is already gone (secret spawned) but no
  carryable copy exists for P2 — `P2_TryLift.spawn` (`:1636-1651`) just
  returns via `.done` without setting `P2_LiftTimer`. Checked against
  vanilla's own `Link_PerformThrow` (usdasm `bank_07.asm:10086-10168`): it
  has the *identical* two-step structure (free-slot pre-check at
  `.next_sprite`, `bank_07.asm:10097-10104`, then lift-and-maybe-spawn-secret,
  then a second, unguarded `JSL Sprite_SpawnThrowableTerrain`), so this is an
  **inherited vanilla edge case**, not new in P2. NOTES.md's own "not
  verified" list already flags dungeons-with-HP-enemies as untested, which is
  exactly the scenario (a near-full sprite table) that would trigger this.
- **Room/area transitions:** `P2_Stash`/`P2_Unstash`
  (`player2.asm:1688-1714`), driven from `P2_CheckRoomChange`
  (`player2.asm:305-322`) on any indoor-room (`$A0`) or outdoor-area (`$8A`)
  ID change. Verified in NOTES.md's "Door (v16)" check (bush survives a real
  house transition both directions) — runtime-tested, not just
  static-reviewed.
- **Dying while carrying / Link carrying at the same time:** not covered by
  any special-case code; P2's own death/hide path (`P2_Draw`'s module/flag
  gating) simply stops drawing/updating P2, and the held object (a live,
  independent vanilla sprite) is unaffected by P2 disappearing until the next
  `P2_HoldObject` call finds `P2_HeldSlot` still valid and keeps placing it —
  if P2 is hidden (module check fails) `P2_Update`/`P2_HoldObject` still run
  every frame regardless of `P2_Draw`'s own visibility gate (they're called
  unconditionally from `P2_Update`, `player2.asm:285`), so the object keeps
  following P2's last position even while P2 itself isn't drawn. This was
  **not exercised in Mesen2** per NOTES.md's "Not verified" list — INFERRED
  only.
- **Cutscene modules ($0C/$0D/$0E):** `P2_CanAct` (`player2.asm:214-227`)
  gates all input-driven state changes (join/move/attack/lift/leave) on
  module `$07`/`$09`, `$11==0`, `$0FC1==0` (sprites not frozen) and
  `InCutScene==0`; `P2_ReadPad` (`player2.asm:174-194`) separately zeroes all
  pad-2 state whenever `InCutScene` is set. Module `$0E` is handled
  specially only in `P2_Draw` (draw-but-freeze, matching Link) — a held
  object is not specifically frozen/hidden for `$0E`, but since `P2_Update`
  (and thus `P2_HoldObject`) is gated off by `P2_CanAct` for any module other
  than `$07`/`$09`, the object simply stops being repositioned while the menu
  is up, matching Link's own frozen carry pose. Not runtime-tested for the
  carrying case specifically.

## 4. PvP

- **Damage/knockback paths:** `P2_LinkHitsP2` (`player2.asm:1463-1510`) and
  `P2_P2HitsLink` (`player2.asm:1512-1547`), called every frame from `P2_PvP`
  (`player2.asm:1457-1461`, itself called from `P2_Update`, `:287`).
- **Can PvP kill Link or softlock:** No — by design and by code. Neither path
  touches hearts/`$0373` at all (only recoil registers and blink timers),
  matching "no hearts lost" in DESIGN.md/NOTES.md. No path was found where a
  recoil/blink timer fails to reach 0 (both are simple `DEC`-to-zero
  countdowns with no re-trigger while active), so no softlock.
- **Invincibility-frame respect, both directions, VERIFIED against vanilla
  semantics:**
  - `P2_LinkHitsP2` skips if `P2_HurtTimer|P2_RecoilTimer|P2_HopZ != 0` or P2
    isn't placed (`player2.asm:1469-1470`).
  - `P2_P2HitsLink` skips unless `$5D == 0` (`LinkState`,
    `Core/link.asm:97` — default state only) and `$4D|$031F|$037B == 0`
    (`player2.asm:1517-1518`); `$037B` was independently confirmed in usdasm
    (`bank_07.asm:78091-78094`) to be Link's real invincibility gate —
    `Link_ControlHandler` skips applying any pending `$0373` damage whenever
    `$037B != 0`. `P2_TryHurt` (the shared-hearts path, unrelated to PvP)
    checks the same `$037B` flag at `player2.asm:848` before adding to
    `$0373` — consistent, VERIFIED correct reuse of the real gate.
  - `P2_HitLink` (once-per-swing) and the thrust-frame window
    (`CMP #$0B`/`CMP #$04`) prevent P2 from re-hitting Link every frame of
    one swing; same pattern mirrored for P2's own hurtbox via
    `P2_PunchHitsSprite`'s `P2_HitMask`.
- **Simultaneous contact gap:** see Summary #5 — one enemy touching both
  players in the same frame only damages Link that frame (`P2_ContactGate`'s
  `BCS .link_hit` shortcuts before `P2_TryHurt` runs). Narrow, self-correcting
  next frame, LOW severity.
- **Shield interaction:** none today (shield is fully vanilla-passive per
  `Docs/Planning/Plans/shield_interactions_plan_2026-09-25.md` section 1) —
  see Summary #7 for the future-hook coordination note.
- **Sword level / recoil state machine:** P1's sword level and art are read
  live every swing (`P2_ChooseWeapon`, `player2.asm:1342-1353`,
  `$7EF359`/`$7EF3CC`), and Link's own recoil in `P2_P2HitsLink`
  (`:1533-1541`) is driven by writing the *exact* fields
  `LinkState_Recoil` reads (`$27/$28/$29/$C7/$24/$25/$46/$4D` — cross-checked
  names against `Core/link.asm:18-20` `LinkRecoilY/X/Z`), not by calling into
  `LinkState_Recoil` itself — i.e., P2 sets Link's state up for the *next*
  frame's `Link_ControlHandler` dispatch (`$5D` is not written here, so this
  relies on some other path setting `$5D` = the recoil state; **not traced
  further given time budget — flag as INFERRED, not independently confirmed
  that `$5D` gets set to the recoil-state index anywhere in this swing**).

  four pad-2 B presses, the pad-2 mirrors $F1/$F3/$F5/$F7 stayed $00 every frame
  and $037F stayed $00. The vanilla $F5 bit-7 check reads a byte the NMI never
  writes (the pad-2 mirror block is dead in this ROM), so it cannot fire. Keep
  P2 off $F1-$F7 so it stays that way. Downgraded to LOW (latent).
- MEDIUM "!ENABLE_NATIVE_2P_POC defined twice": by design. Every flag has a
  default in Util/macros.asm and an override in Config/feature_flags.asm
  (Scripts/Build/set_feature_flags.py). Not a finding.
- MEDIUM "sword/PvP/lift block assert only checks the bank end": valid. The
  block ends at $3AE64C and Impa hints start at $3AE800; add an assert against
  $3AE800.
